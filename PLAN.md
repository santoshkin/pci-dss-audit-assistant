=== 24.08
# Задача

Разработай полностью локальную систему RAG (Retrieval-Augmented Generation) для работы с документацией PCI DSS.

Среда:

* ОС: Ubuntu Linux
* LLM runtime: Ollama
* Все данные должны обрабатываться локально.
* Никакие документы PCI DSS, пользовательские вопросы или результаты анализа не должны отправляться во внешние облачные API.
* Архитектура должна позволять в будущем подключить LoRA/QLoRA для специализированного дообучения модели.

Главная цель системы:

> Пользователь задаёт вопрос по PCI DSS, а система находит релевантные требования и supporting documentation, передаёт найденный контекст локальной LLM через Ollama и формирует ответ с точными ссылками на документы, версии, Requirement, Testing Procedure и страницы.

---

# 1. Основные требования

Система должна:

1. Индексировать документацию PCI DSS.
2. Поддерживать PDF и текстовые документы.
3. Извлекать структуру документов.
4. Сохранять:

   * название документа;
   * версию;
   * дату;
   * номер страницы;
   * раздел;
   * Requirement;
   * Testing Procedure;
   * Guidance;
   * тип документа.
5. Разбивать документы на семантические chunks.
6. Создавать embeddings локально.
7. Хранить embeddings в локальной vector database.
8. Выполнять semantic search.
9. Желательно использовать hybrid search:

   * vector search;
   * keyword/BM25 search.
10. Использовать reranking найденных результатов.
11. Передавать наиболее релевантные результаты в Ollama.
12. Генерировать ответ только на основе найденного контекста.
13. Всегда указывать источники.
14. Не придумывать номера PCI DSS requirements.
15. Если информации недостаточно — явно сообщать об этом.
16. Различать PCI DSS версии.
17. Не смешивать требования разных версий без явного указания.
18. Поддерживать обновление документов без полного пересоздания всей системы.

# 6. Metadata

Metadata имеет критическое значение.

Для каждого chunk сохраняй примерно:

{
"document_id": "...",
"document_title": "...",
"document_type": "pci_dss|faq|guidance|supplement",
"version": "4.0.1",
"publication_date": "...",
"page": 123,
"section": "...",
"requirement": "8.4.2",
"testing_procedure": "8.4.2.a",
"chunk_type": "requirement|testing_procedure|guidance|definition|other",
"source_file": "...",
"text": "..."
}

Если metadata невозможно определить автоматически, оставляй null, а не выдумывай значение.

---

# 7. Chunking

Не используй исключительно механическое разбиение:

chunk_size = 1000

Нужно реализовать semantic/structure-aware chunking.

Особенно важно сохранять вместе:

Requirement
↓
Requirement text
↓
Testing Procedures
↓
Guidance

Например Requirement 8.4.2 должен оставаться логически связанным с Testing Procedure 8.4.2.a.

Не допускай ситуации, когда Requirement находится в одном chunk, а его Testing Procedure случайно оказывается в другом несвязанном документе.

Предусмотри parent/child chunks, если это улучшает качество retrieval.

# 8. Retrieval

Реализуй pipeline:

User Query
↓
Query preprocessing
↓
Vector search
+
BM25 keyword search
↓
Merge
↓
Reranking
↓
Top K context
↓
LLM

Особенно хорошо должны находиться запросы вида:

"Какое требование касается административного доступа?"

"Что требуется для cloud environment?"

# 9. Поиск по Requirement ID

Система должна отдельно распознавать номера требований.

Например:

8.4.2
10.4.2
1.2.4

Если пользователь спрашивает:

"Расскажи про 8.4.2"

система не должна полагаться только на embedding search.

Сначала должен выполняться точный поиск metadata:

requirement = "8.4.2"

и только потом semantic retrieval.

# 10. Версии

Версия PCI DSS является обязательной частью metadata.

Например:

version = 4.0.1

Не смешивай:

PCI DSS 3.2.1
PCI DSS 4.0
PCI DSS 4.0.1

без явного указания.

Если пользователь не указал версию, используй актуальную версию, которая присутствует в базе, но сообщай её в ответе.

Предусмотри возможность в будущем добавить новую версию.

# 11. Prompt для LLM

Создай отдельный системный prompt для PCI DSS Assistant.

Главные правила:

* Отвечай только на основании предоставленного контекста.
* Не выдумывай PCI DSS requirements.
* Не выдумывай Testing Procedures.
* Не выдумывай номера страниц.
* Не утверждай, что требование применимо, если контекст этого не подтверждает.
* Разделяй:

  * Requirement;
  * Testing Procedure;
  * Guidance;
  * Interpretation.
* Если делаешь вывод, который является интерпретацией, явно помечай его как interpretation.
* Если информации недостаточно, скажи:
  "Недостаточно информации в доступных источниках."
* Всегда указывай источники.

Ответ желательно формировать в формате:

...

### PCI DSS v4.0.1 — Requirement X.X.X

...

### Testing Procedure

...

## Анализ

...

## Необходимые evidence

* ...
* ...
* ...

## Возможные gaps

* ...
* ...

## Рекомендации

* ...

## Источники

* PCI DSS v4.0.1, Requirement X.X.X, page ...
* ...

Не генерируй citation самостоятельно.

=== 25.08

# PCI DSS RAG / Audit Assistant — обновлённый план

Версия документа: v1 (составлен по итогам опроса, 2026-08-25)
Статус: проектирование, до начала разработки кода

## 0. Что меняется относительно исходного ТЗ

Исходное ТЗ описывало «RAG по стандарту PCI DSS». По итогам ответов задача шире:
инструмент для команды из нескольких внешних аудиторов, который (а) ищет и
объясняет требования стандарта, (б) ведёт клиентские аудиторские проекты
(evidence, findings, статус по каждому requirement) и (в) генерирует
черновики отчётных документов (ROC, AOC, Action Plan) по заранее загруженным
шаблонам. Технологический стек (Ollama, Qdrant, локальные embeddings)
остаётся, но модель данных и архитектура развёртывания меняются: нужен
явный слой «клиентских проектов», отдельный от базы знаний стандарта, плюс
реляционное хранилище для структурированных сущностей (клиенты, findings,
статусы, версии отчётов), которого в исходном плане не было.

Ключевые решения, вытекающие из ответов:

- **Мультиклиентность и изоляция.** Несколько аудиторов, несколько
  параллельных проектов, данные клиентов не должны пересекаться между собой
  (25 — нет), но общая база знаний PCI DSS переиспользуется всеми (24 — да,
  но это про изоляцию клиентских данных, не про сам стандарт).
- **Развёртывание.** Разработка — на одной машине, прод — выделенный сервер
  компании (2× RTX 3090 или 3090+4090, 64 ГБ RAM, ~1 ТБ диска), Ollama уже
  установлен и обслуживает несколько сервисов. RAG API и Qdrant должны уметь
  обращаться к Ollama по сети (`OLLAMA_BASE_URL` на другой хост), а не только
  `localhost`.
- **Интернет.** Разрешён при установке/обновлении моделей, запрещён в
  runtime для любых пользовательских/клиентских данных (81).
- **Человек всегда в контуре.** Отчёты всегда проверяются аудитором перед
  отправкой клиенку (76) — это снижает требования к жёсткому
  confidence-gating на этапе генерации отчёта, но не отменяет его для
  «быстрого поиска по стандарту» в live-режиме.
- **Отчётность — это отдельный, приоритетный модуль**, а не «фича на
  будущее»: ROC/AOC (англ.) и Action Plan (рус.) по загружаемым шаблонам,
  с ID/Requirement/Testing Procedure/описанием несоответствия/рекомендацией
  как минимальным набором полей (71, 73, 80).
- **LoRA откладывается «on paper»** (53), но если и делать — то под
  классификацию applicability requirements (54), значит эта функциональность
  проектируется как отдельный classification-сервис, не как часть retrieval.
- **Анонимизация — вне scope**, для неё уже есть отдельный инструмент (85).
- **Web UI — после API/CLI**, не в MVP (88).

## 1. Архитектура (обновлённая)

```
                         │   Внутренняя сеть компании (без internet)│

  (разработка, тесты) ───┼──▶  Ollama (LLM + embeddings, shared)    │
                         │        │                                  │
                         │        ▼                                  │
                         │   ┌─────────────────────────────────┐    │
                         │   │  RAG / Audit Assistant API       │    │
                         │   │  (FastAPI, Docker)               │    │
                         │   │                                   │    │
                         │   │  ┌─────────────┐ ┌──────────────┐│    │
                         │   │  │ Knowledge    │ │ Client        ││    │
                         │   │  │ Base module  │ │ Workspace     ││    │
                         │   │  │ (PCI DSS,    │ │ module        ││    │
                         │   │  │ FAQ, Guidance)│ │ (проекты,     ││    │
                         │   │  │ - shared     │ │ evidence,     ││    │
                         │   │  │ Qdrant coll. │ │ findings)     ││    │
                         │   │  └─────┬───────┘ └──────┬────────┘│    │
                         │   │        │  hybrid search   │         │    │
                         │   │        ▼                  ▼         │    │
                         │   │   Reranker  ──▶  Context builder     │    │
                         │   │                        │              │    │
                         │   │                        ▼              │    │
                         │   │                 Ollama generation     │    │
                         │   │                        │              │    │
                         │   │                        ▼              │    │
                         │   │              Report generator (docx)  │    │
                         │   └───────────────────────────────────────┘    │
                         │                                                 │
                         │   Qdrant (Docker) ── per-client collections    │
                         │   Postgres/SQLite ── структурные данные:        │
                         │     клиенты, проекты, findings, статусы,        │
                         │     версии отчётов, аудит-лог                    │
                         └─────────────────────────────────────────┘
```

Главное архитектурное отличие от исходного плана — появление второго
хранилища данных. Qdrant хорошо подходит для векторного поиска по тексту, но
плохо подходит для структурированных, изменяемых во времени сущностей
(«статус Requirement 8.4.2 для клиента X = Non-Compliant, назначен на
аудитора Y, дедлайн ремедиации — дата»). Такие данные нужно хранить в
реляционной БД (Postgres — рекомендация, с учётом нескольких параллельных
пользователей; SQLite достаточен только для однопользовательского прототипа
и не подходит при реальной многопользовательской работе с блокировками
записи). Qdrant при этом хранит embeddings текста (стандарта и клиентских
документов), Postgres — связи, статусы, версии, права доступа.

## 2. Модель данных (новое / расширенное)

Помимо `Chunk` (как в исходном ТЗ) добавляются сущности:

- **Organization / Client** — заказчик аудита.
- **AuditProject** — конкретный аудиторский проект у клиента (может быть
  несколько активных одновременно на разных стадиях — под это нужен явный
  статус проекта: сбор evidence / анализ / черновик отчёта / согласование /
  закрыт).
- **RequirementCatalog** — нормализованный справочник requirement/testing
  procedure ID из актуальной версии стандарта (для точного lookup, п.9
  исходного ТЗ, плюс нечёткий/опечаточный поиск по ID, вопрос 64).
- **RequirementStatus** (per AuditProject × Requirement) — Compliant /
  Non-Compliant / N/A / Compensating Control / In Progress, с ссылкой на
  findings и evidence.
- **Evidence** — файл или фрагмент (конфиг, скриншот, транскрипт интервью,
  политика заказчика), с привязкой к одному или нескольким requirement.
  Тоже чанкуется и индексируется, но в **клиентской** Qdrant-коллекции, не в
  общей базе стандарта.
- **Finding** — зафиксированное несоответствие: requirement, описание
  недостатка, рекомендация, кто/когда создал, статус (draft/reviewed/final).
- **ReportTemplate** — загружаемый заранее шаблон (docx) с плейсхолдерами:
  ROC, AOC, Action Plan; может быть несколько вариантов на выбор (73).
- **ReportRun** — конкретная генерация отчёта: какой шаблон, какой проект,
  кто запустил, какие findings вошли, статус проверки человеком.
- **User** — аудитор/администратор, роль (29).

Изоляция клиентов реализуется на двух уровнях: отдельная Qdrant-коллекция
на клиента (evidence этого клиента никогда не попадает retrieval-ом в
контекст другого клиента) и `AuditProject.organization_id` как обязательный
фильтр на уровне API для всех структурированных запросов.

## 3. Модули и приоритеты (переработанные фазы)

### Фаза 0 — Core Knowledge RAG (по сути исходный MVP)
Индексация официальных документов Совета PCI SSC (стандарт, FAQ, Guidance,
Supplements, SAQ, глоссарий) только актуальной версии + русский перевод как
отдельный документ с тем же `requirement_id`, но своим `language`/`source`
в metadata (39, 38, 35). Structure-aware chunking, hybrid retrieval (BM25 +
vector), reranker, точный lookup по requirement ID с нечётким совпадением
(rapidfuzz), Ollama generation с системным промптом «только на основе
контекста». CLI + API, без веб-интерфейса.

Проверка: `python -m app.ingest`, затем `python -m app.chat "..."` даёт
корректные ссылки на Requirement/Testing Procedure/страницу.

### Фаза 1 — Client Workspace + Findings
Postgres-схема (Client, AuditProject, RequirementStatus, Finding, User).
API для создания проекта, привязки findings к requirement, отметки статуса.
Пока без генерации отчёта — просто структурированное ведение аудита вместо
исходного Excel/Word. Здесь же — режим «работа в контексте клиента» (90):
выбрал проект — все последующие вопросы/поиски идут с учётом клиентской
Qdrant-коллекции этого проекта поверх общей базы стандарта.

### Фаза 2 — Evidence intake
Загрузка и обработка клиентских artefacts: транскрипты интервью (текст),
документы заказчика (PDF/docx), выгрузки конфигураций (текст/JSON/CSV) как
evidence. Тот же ingestion-пайплайн, что и для стандарта, но с другой
schema метаданных (без requirement/testing_procedure по умолчанию — их
проставляет аудитор вручную или подсказывает LLM как черновик привязки,
которую человек подтверждает).

### Фаза 3 — Report generation (ROC / AOC / Action Plan)
Движок заполнения docx-шаблонов на основе findings проекта. Action Plan —
всегда на русском (формат ID / Requirement или Testing Procedure / описание
несоответствия / рекомендация, п.71); ROC/AOC — на английском, по
официальной структуре. Генерация — только черновик, обязательный шаг
review человеком перед финалом (76), с версионированием ReportRun.
Библиотека готовых формулировок (78) хранится отдельно и подмешивается в
промпт как few-shot примеры стиля, не как источник фактов.

### Фаза 4 — Web UI
Простой FastAPI + HTMX интерфейс поверх уже готового API: выбор
проекта/клиента, чат с историей (89 — нет для истории вообще, но 91 нет,
90 — да контекст проекта нужен, значит UI при этом всё равно проектный).
Ничего сверх необходимого — ролевой доступ auditor/admin (29).

### Фаза 5 (дальше, месяцы) — Scope / Gap-analysis из описания инфраструктуры
Приоритетное направление после MVP по вашему ответу (98): на вход —
текстовое описание инфраструктуры или набор evidence/интервью, на выходе —
предполагаемый scope, применимые requirements, недостающие evidence,
черновой gap-analysis. Технически это отдельный agentic-слой поверх Фазы
0–3: LLM формирует гипотезы применимости → RAG подтверждает каждую ссылкой
на конкретный requirement → человек проверяет. Не путать с LoRA — это
отдельный классификационный сервис, на который впоследствии можно навесить
LoRA-адаптер (applicability classification, п.53–54) без изменения самого
RAG pipeline, как и было заложено в исходном ТЗ.

## 4. Технологический стек (уточнён)

- **LLM:** через Ollama, модель на старте `qwen3.6:27b` (уже используется),
  доступ к Ollama по сети (`OLLAMA_BASE_URL=http://<prod-host>:11434`), а не
  хардкод localhost — важно для разработки на одной машине / прода на
  другой.
- **Embeddings:** локальная модель с хорошей поддержкой русского и
  кросс-язычным сопоставлением рус. вопрос → англ. документ. Кандидаты:
  `BAAI/bge-m3` (мультиязычный, хорошо показывает себя на RU/EN) или
  `intfloat/multilingual-e5-large`. Выбор — по факту тестирования на вашем
  корпусе (37, 51).
- **Vector DB:** Qdrant в Docker, отдельная коллекция на knowledge base +
  по коллекции на каждый клиентский проект.
- **Реляционная БД:** PostgreSQL в Docker (учитывая многопользовательский
  доступ по сети, 48).
- **Document parsing:** PDF с текстовым слоем (не сканы, 36) — `pdfplumber`
  или `PyMuPDF` для точного постраничного/табличного извлечения структуры
  Requirement/Testing Procedure/Guidance; OCR-фолбэк не приоритет, но
  оставить точку расширения.
- **Report generation:** `python-docx` для заполнения docx-шаблонов
  (используем `docx`-skill на этапе реализации).
- **Fuzzy requirement ID search:** `rapidfuzz` поверх нормализованного
  regex-парсера номеров вида `\d+(\.\d+){1,3}`.
- **Reranker:** локальная cross-encoder модель (например,
  `BAAI/bge-reranker-v2-m3`, мультиязычная).
- **Backend:** Python + FastAPI, Docker Compose (Qdrant + Postgres + API;
  Ollama остаётся на хосте).

## 5. Что осознанно НЕ делаем на первых фазах

- Web UI (88) — после API/CLI.
- Анонимизация данных — уже есть отдельный инструмент (85).
- Жёсткий hard-block по confidence на этапе отчёта — контроль всегда
  человеком (76); confidence-предупреждение оставляем только как сигнал
  в live-чате аудитора, не как блокировку отчёта.
- Поддержка нескольких версий PCI DSS одновременно — только актуальная
  версия сейчас (35), но схема данных версию всё равно хранит, чтобы не
  переделывать при добавлении 3.2.1 позже.
- Автоматическая работа без проверки эксперта в отчётах — исключено
  архитектурно на всех фазах, где есть клиентский вывод.

## 7. Решения по итогам второго опроса (25.08, вечер)

1. **Requirement Catalog** — извлекается автоматически из PDF стандарта при
   индексации (без отдельного эталонного CSV/JSON). Риск: качество
   справочника целиком зависит от парсера и структуры конкретного PDF —
   в Фазе 0 нужен явный шаг валидации (например, сверка количества найденных
   requirement ID с ожидаемым диапазоном по разделам стандарта) и логирование
   ID, которые не удалось распознать, вместо тихого пропуска.
2. **Postgres** — новый инстанс в `docker-compose.yml` проекта, не общий с
   другими системами компании. Упрощает миграции, бэкап/restore и не создаёт
   зависимости от внешней инфраструктуры.
3. **ROC/AOC шаблоны** — Фаза 3 (Report generation) **блокируется** до
   получения официальных docx-шаблонов ROC/AOC от PCI SSC (или используемых
   в компании). До их получения Фазы 0–2 разрабатываются как запланировано;
   структура плейсхолдеров для Фазы 3 проектируется только после того, как
   шаблоны будут предоставлены.
4. **Embedding и reranker — через Ollama API**, не отдельным процессом.
   Технический риск, требующий проверки до начала Фазы 0: Ollama имеет
   стабильный `/api/embed` для embedding-моделей (bge-m3 и аналоги там
   присутствуют), но **нативного эндпоинта для cross-encoder reranking
   исторически нет** — bge-reranker-v2-m3 и подобные модели по архитектуре
   не являются causal LM и штатно не запускаются как generate/chat модель в
   Ollama. Перед реализацией Фазы 0 нужно явно проверить на прод-сервере:
   - доступна ли выбранная reranker-модель через Ollama (`ollama list`,
     `ollama show`) и поддерживает ли установленная версия Ollama
     rerank-подобный вызов;
   - если нет — зафиксировать fallback: либо reranking через обычный
     `/api/embed` с ручным cosine-scoring (без настоящего cross-encoder,
     хуже качеством), либо через generate-модель с промптом
     "оцени релевantность" (хуже по скорости/стабильности), либо всё же
     отдельный процесс только для reranker (embedding остаётся на Ollama).
   Это первое, что нужно протестировать технически перед началом кода —
   см. раздел 8.

## 8. Роль архитектора/тестировщика — план проверки перед кодом

Прежде чем писать код Фазы 0, нужно верифицировать техническими средствами
(не на словах) следующие допущения архитектуры:

1. **Ollama embed/rerank capability check** — скрипт, который дергает
   реальный Ollama на прод-хосте (`OLLAMA_BASE_URL`), проверяет наличие
   `bge-m3` (или выбранной embedding-модели) и пытается вызвать embedding;
   отдельно проверяет, есть ли способ получить rerank-score через API текущей
   версии Ollama. Результат определяет, остаётся ли решение "reranker через
   Ollama" в силе или переходим на fallback.
2. **PDF structure extraction smoke test** — прогон парсера (`pdfplumber`/
   `PyMuPDF`) на реальном PDF PCI DSS v4.0.1, подсчёт найденных Requirement
   ID и сверка на выборке вручную (10–15 requirement) — до того, как на этом
   парсере строится вся цепочка chunking/metadata.
3. **Qdrant + Postgres compose smoke test** — `docker compose up` поднимает
   оба контейнера, health-check проходит, миграции Postgres применяются.

Эти три проверки — предварительное условие входа в Фазу 0, а не часть самой
Фазы 0: если Ollama не поддерживает reranking нативно, это меняет состав
`requirements.txt` и раздел "Технологический стек" до того, как написана
первая строчка кода retrieval-пайплайна.
